# Возобновление и перемотка

Это руководство возобновляет работу сервиса с места, где остановился его прошлый запуск, и переносит работающую подписку в другое место файла.

Файл потока не хранит, докуда дочитал читатель.
`ack` и `nack` на этом транспорте возвращают `Unsupported` ([Подтверждение](../components/settlement/index.md)), поэтому перезапущенная подписка открывается там, где указывает её точка монтирования.
Сервис, которому нельзя обработать заказ дважды, сам хранит свою контрольную точку.

Пример - сервис выставления счетов: он читает заказы магазина и выставляет счёт на каждый ровно один раз, в том числе между перезапусками.

Контрольная точка - это порядковый номер последнего заказа, на который сервис выставил счёт, в отдельном файле.
`Invoicing` - состояние приложения, и обработчик берёт контрольную точку из него.
Так же работает любое хранилище, которое уже есть у сервиса: строка в базе данных, ключ в кеше.

`invoicing` читает контрольную точку до запуска сервиса и передаёт её в [`start_at`](../components/positions/start-at.md) в точке монтирования.
У первого запуска контрольной точки нет, и он читает файл с начала.
[`FilePosition::sequence(n)`](../components/positions/index.md) доставляет и само сообщение `n`, поэтому запуск, открытый на сохранённом номере, ещё раз получает заказ, на котором закончился прошлый.
`invoice` читает порядковый номер доставки через [`Ctx<Position>`](../components/positions/position.md) и отбрасывает заказ с номером не больше контрольной точки.
На каждый другой заказ выставляется счёт, и его номер становится новой контрольной точкой.

Контрольная точка записывается после счёта.
Если запуск останавливается между ними, следующий запуск снова выставляет счёт на этот заказ, поэтому само выставление счёта должно допускать повтор.
Запись контрольной точки до счёта даёт обратный компромисс: счёт на заказ никогда не выставляется дважды, но один заказ может потеряться.

[`FilePosition::timestamp(ms)`](api:ruststream_sea_file::FilePosition::timestamp) открывает подписку на первом сообщении, записанном после заданного момента, в миллисекундах от начала эпохи Unix.
Эта позиция подходит сервису, который восстанавливает своё представление данных с момента времени, а не с сохранённого номера.

## Перемотка работающей подписки {/* #moving-a-running-subscription */}

Обработчик перематывает собственную подписку через [`Ctx<SeekHandle>`](../components/positions/seek.md).
`seek(FilePosition::end())` пропускает накопленное и продолжает с конца журнала. `seek(FilePosition::sequence(n))` возвращается к сообщению `n` или перескакивает вперёд через ряд сообщений, о которых известно, что они не обрабатываются.
Доставки, которые уже стоят в очереди со старого места, отбрасываются, и следующая доставка приходит с нового.
Перемотка на порядковый номер дальше того, который файл запишет следующим, возвращает ошибку: живая подписка тогда заканчивается, а [воспроизведение](../components/subscriptions/replay.md) остаётся на месте.
Пакетный обработчик получает тот же дескриптор через [`FileBatchContext`](../components/positions/batch-context.md).

## Тестирование возобновления {/* #testing-the-resume */}

Внутрипроцессные тесты записывают пять заказов до запуска сервиса и сохраняют контрольную точку со значением три.
Сервис читает заказы с третьего по пятый, отбрасывает третий и выставляет счета на два других.
Тест перезапуска дважды запускает сервис на одном настоящем файле через [`TestApp::start_live`](../components/testing/live.md): второй запуск открывается на заказе, которым закончился первый, и отбрасывает его.
Оба режима разбирает руководство [Тестирование сервиса на файле или в конвейере](testing.md).
