# Файлы и stdio

`ruststream-sea-file` запускает сервис RustStream вообще без сервера: на долговечном
воспроизводимом файле потока на диске или на собственных стандартных вводе и выводе процесса.
Подписчиков, маршрутизацию, кодеки и middleware даёт фреймворк, и они описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/); эта страница - о двух
транспортах.

```toml
ruststream = { version = "0.7", features = ["macros", "json"] }
ruststream-sea-file = "0.7"
serde = { version = "1", features = ["derive"] }
```

Файловый транспорт не собирается под Windows: лежащий в его основе файловый клиент работает только
на Unix.

## Совместимости {#capabilities}

Какие необязательные трейты-совместимости фреймворка реализует этот крейт и что даёт каждый из них:

| Совместимость | Реализована | Примечания |
| --- | --- | --- |
| `Subscribe` | Да | Ключ потока вы называете строковым литералом на любом из транспортов, и `#[subscriber("key")]` обходится без дескриптора. См. [Подписки](#subscriptions). |
| `Seekable` + `Positioned` | `Positioned` на обоих, `Seekable` на файле | Каждая доставка сообщает номер последовательности, на котором она стоит. Обработчик на файле потока ещё и передвигает собственную подписку через ключи контекста `Position` и `SeekHandle`, и этот крейт - эталонная реализация такой совместимости во фреймворке. Подписка на stdio не двигается: стандартный ввод не хранит журнала, внутри которого можно двигаться. См. [Перемотку](#seeking). |
| `Partitioned` | Нет | Файл потока - один упорядоченный журнал без шардов. |
| `BatchSubscriber` | Да, на стороне клиента | `batch(n)` вы называете в точке монтирования и получаете пакеты не больше `n` на любом из транспортов. См. [Пакеты](#batches). |
| `RequestReply` | Нет | Ни у одного из транспортов нет адреса для ответа. |
| `TransactionalPublisher` | Нет | У файла потока нет единицы атомарной групповой записи: каждая публикация дописывает и сбрасывает на диск сама по себе. |
| `OwnedTransactions` | Нет | По той же причине: владеть нечем, транзакции нет. |
| `DescribeServer` | Да | Сгенерированный документ AsyncAPI называет внутрипроцессный сервер: `file` с путём или `stdio`. |

`ack` и `nack` на обоих транспортах возвращают `AckError::Unsupported`: клиент не записывает позиции
консьюмеров, а его режим с возобновлением в апстриме не реализован. См.
[Подтверждение](#acknowledgement).

## Два брокера {#the-two-brokers}

У каждого транспорта свой модуль с типами этого транспорта, его политикой `Publish` и его
прелюдией. Сервис на файлах потоков открывается строкой `use ruststream_sea_file::file::prelude::*;`,
сервис на конвейере - строкой `use ruststream_sea_file::stdio::prelude::*;`, и больше из этого
крейта не импортирует ничего.

Сервис, который работает с обоими, берёт glob `ruststream_sea_file::prelude` и пишет `FilePublish`
и `StdioPublish` с префиксом, потому что иначе две формы заняли бы одно имя политики.

`FileBroker::new(path)` записывает путь к файлу потока `.ss`. `StdioBroker::new()` не записывает
ничего. Открытие и закрытие происходят в переходах, которые идут дальше:

```text
FileBroker::new(path)      только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedFileBroker      открытый файл; подписки и издатели
  .shutdown()  ->  ()                       сброшено на диск и закрыто
```

Издатель, выданный до остановки, разделяет соединение брокера: после закрытия брокера он возвращает
ошибку `SeaFileError::NotConnected`, а не молча сообщает об успехе.

`FileBroker` принимает три необязательные настройки, и все они применяются при подключении:

- `existing_only()` требует, чтобы файл уже существовал, вместо того чтобы создавать его.
- `end_with_eos()` пишет при остановке метку конца потока, поэтому консьюмер, воспроизводящий
  законченный файл, завершается, а не ждёт новых данных.
- `beacon_interval(bytes)` задаёт, на каком расстоянии в байтах стоят записи встроенного индекса
  файла; значение должно быть положительным кратным 1024. Чем плотнее маяки, тем точнее перемотка и
  тем больше файл.

Остановка stdio-брокера завершает все stdio-консьюмеры и продюсеры в процессе, а не только
открытые этим брокером.

## Подписки {#subscriptions}

`FileStream::new(key)` - дескриптор подписки на один ключ потока в файле. Он пишется прямо в
атрибуте `#[subscriber(..)]`, и обычный дескриптор следует за живым хвостом:

```rust
--8<-- "crates/ruststream-sea-file/examples/file_service.rs:handler"
```

Смонтируйте его на брокере:

```rust
--8<-- "crates/ruststream-sea-file/examples/file_service.rs:app"
```

Ручной путь принимает тот же дескриптор: `subscriber(FileStream::new("orders"), body)`.

На stdio-брокере подписка - это сам ключ потока: `#[subscriber("jobs")]` читает ключ `jobs` со
стандартного ввода.

### Режим воспроизведения {#replay-mode}

`FileStream::new(key).replay()` читает файл с начала и завершает подписку в конце файла, вместо
того чтобы следовать за живой записью. Так вы обрабатываете записанный журнал за один проход. Файл,
записанный с `end_with_eos()`, заканчивается меткой, на которой воспроизведение останавливается.

Воспроизведение - единственный режим чтения, который нельзя выразить позицией.

### Пакеты {#batches}

Обработчик, который принимает `&[T]`, получает пакет:

```rust
--8<-- "crates/ruststream-sea-file/examples/file_batches.rs:batch"
```

а размер пакета называет точка монтирования:

```rust
--8<-- "crates/ruststream-sea-file/examples/file_batches.rs:mount"
```

Оба клиента читают по одной записи за раз, поэтому пакет собирается на стороне клиента. Пакет
никогда не содержит больше сообщений, чем названо в точке монтирования, и содержит меньше, когда
больше у транспорта не было.

Неполный пакет уходит через 10 мс после первой доставки. Этот срок здесь фиксирован: точка
монтирования его не меняет. Он ограничивает то, как долго пакет ждёт на простаивающем хвосте.

## Перемотка {#seeking}

Подписка на файле потока переходит на любую позицию в сохранённом журнале. Позиция - это
`FilePosition`:

| Позиция | Значение |
| --- | --- |
| `FilePosition::beginning()` | Начало сохранённого файла. |
| `FilePosition::end()` | Конец потока. |
| `FilePosition::sequence(n)` | Сообщение с номером `n`, доставляется повторно включительно. |
| `FilePosition::timestamp(millis)` | Первое сообщение строго позже этого момента; `millis` - миллисекунды с начала эпохи Unix. |

Позиция, снятая с доставки, закреплена: перемотка обратно на неё доставляет повторно ровно это
сообщение, а затем остаток журнала по порядку.

Клауза `start_at(..)` в атрибуте говорит, где подписка начинается, до её первой доставки.
Работающий обработчик передвигает собственную подписку через два ключа контекста:

| Ключ | Читает | Доступен на |
| --- | --- | --- |
| `Position` | `FilePosition` этой доставки | `FileContext` |
| `SeekHandle` | дескриптор, который передвигает подписку | `FileContext`, `FileBatchContext` |

Обработчик принимает эти ключи параметрами через экстрактор `Ctx` и не называет тип контекста
вообще.

```rust
--8<-- "crates/ruststream-sea-file/examples/file_replay.rs:seek"
```

[Пакетное](#batches) тело объявляет `ctx: &mut Context<'_, FileBatchContext>` и читает дескриптор
вызовом `ctx.context(SeekHandle)`. Пакет охватывает много доставок, поэтому позиции в этом контексте
нет; собственный номер последовательности каждого элемента лежит в его заголовке `stream-sequence`.

Обработчик, который читает любой из этих ключей, не компилируется против `StdioBroker`: стандартный
ввод не хранит журнала, внутри которого можно двигаться.

Доставки, стоявшие в очереди до перемотки, отбрасываются, поэтому следующее сообщение обработчик
видит уже с новой позиции. Про саму совместимость см.
[Перемотку](https://powersemmi.github.io/ruststream/latest/guides/subscribers/#seeking) в
документации фреймворка.

## Публикация {#publishing}

`FilePublish` - политика, которая конструирует издателя `FilePublisher`, дописывающего в файл
потока; `StdioPublish` конструирует `StdioPublisher`, который пишет строки в стандартный вывод.
Политику вы указываете при регистрации обработчика, а на старте она инстанцирует издателя на
подключённом брокере.

Каждая политика - умолчание своего брокера, поэтому ответ идёт через неё, когда точка монтирования
не называет другую. Другую политику вы называете в точке монтирования через `.out`, сначала маркер,
потом политика: `b.include(handle).out(Reply, Publish);` называет политику для ответа, а внедрённый
слот `Out` принимает её так же, под своим маркером.

Назначение на этом транспорте - ключ потока внутри брокера. Сам файл называется один раз, в
`FileBroker::new(path)`, а форма stdio пишет в стандартный вывод. Поэтому ключ вы можете объявить на
типе ответа через `#[outgoing(name = "results")]` и написать на подписчике клаузу `publish` без
имени.
Ответ, тип которого не объявляет ключ, публикуется туда, куда говорит подписчик:
`publish("results")`.

Каждая прелюдия транспорта экспортирует свою политику под именем `Publish`, поэтому точка
монтирования называет понятие: сервис, переходящий между двумя формами, меняет glob, а не имя
политики.

Файловый издатель сбрасывает данные на диск при каждой публикации, поэтому живой подписчик - или
сторонний читатель того же файла - видит сообщение, как только вызов вернулся.

Публикация из хука старта называет ту же политику:

```rust
--8<-- "crates/ruststream-sea-file/examples/file_replay.rs:publish"
```

На сообщение без полезной нагрузки и без заголовков stdio-издатель возвращает ошибку
`SeaFileError::Invalid`, потому что построчный формат клиента молча отбрасывает пустые строки.

### Аргументы на сообщение {#per-message-arguments}

Обработчик публикует через билдер фреймворка: `publisher.message(&value).publish()`, с шагом
`.to(key)` там, где собственный `#[derive(Outgoing)]` значения оставляет ключ потока вызову. У
сообщения здесь есть ключ потока и полезная нагрузка, и это собственные аргументы билдера.

Непрозрачные байты передаются так же - значением, тип которого объявляет себя уже сериализованным
(`#[derive(Outgoing, Serialized)] struct Frame(Vec<u8>)`), поэтому кодек над ними не работает.

Брокеры, у которых есть поле протокола на сообщение - приоритет, QoS, ключ упорядочивания, -
добавляют в этот билдер шаг для него. У этих двух транспортов такого поля нет: дозапись в файл
потока и строка в стандартном выводе содержат ключ и полезную нагрузку и больше ничего. Поэтому
шага этот крейт не добавляет, а телу обработчика, которое публикует, хватает одной прелюдии
фреймворка и простого ограничения `Out<impl Publisher, Marker>`.

## Конверт заголовков {#the-header-envelope}

Полезная нагрузка у клиента - это просто байты, места для заголовков в ней нет, поэтому заголовки
пишутся в саму полезную нагрузку. Конверт появляется только тогда, когда у сообщения есть
заголовки:

- Сообщение, опубликованное без заголовков, записывается как есть. Файл, записанный так, остаётся
  читаемым как обычный поток полезных нагрузок для любого консьюмера `sea-streamer`, а файл,
  записанный другим инструментом, остаётся читаемым здесь.
- Сообщение с заголовками записывается как `rs1:` и следом base64 от блока заголовков с префиксом
  длины и полезной нагрузки. Форма безопасна для текста, потому что транспорт stdio построчный и в
  UTF-8.

Издатель stdio заворачивает в конверт ещё и полезную нагрузку не в UTF-8, у которой нет заголовков,
поэтому двоичные данные проходят конвейер оболочки без искажений.

У каждой доставки номер последовательности лежит в заголовке `stream-sequence`
(`SEQUENCE_HEADER`).

## Подтверждение {#acknowledgement}

Возобновление на этом транспорте вы делаете явно: сохраните `FilePosition`, снятую с доставки, и
откройте следующий прогон с `start_at(..)` - или воспроизведите файл с начала. `ack` и `nack`
возвращают `AckError::Unsupported`, поэтому больше ничто не записывает, до какого места вы
прочитали.

### Повтор после задержки {#retrying-after-a-delay}

У `HandlerOutcome::retry_after(delay)` здесь нет транспортной опоры, поэтому весь механизм - это
собственный запасной путь фреймворка: он отбрасывает доставку и по истечении задержки публикует
копию сообщения с увеличенным заголовком счётчика повторов. Издателя, которым он пользуется, вы
связываете в корне композиции:

```rust
--8<-- "crates/ruststream-sea-file/tests/redelivery.rs:retry_via"
```

Копия уходит в тот ключ потока, который читает подписка, поэтому живая подписка на файле потока
получает своё сообщение обратно. Воспроизведение - нет: оно читает ту область, которую файл уже
содержал, и завершается, а копия, записанная после, до него не дойдёт. Поэтому область, где
`retry_via` связан поверх подписки `FileStream::replay()`, не запускается и называет эту подписку -
вместо того чтобы отбрасывать каждое отложенное сообщение в рантайме. Stdio отказывается по той же
причине: то, что вы публикуете, уходит следующему процессу в конвейере, а не обратно в ваш
собственный стандартный ввод.

Без `retry_via` `retry_after` деградирует до немедленного возврата в очередь, а на этих транспортах
это означает, что задержка потеряна.

## Конвейеры stdio {#stdio-pipelines}

`StdioBroker` делает процесс ступенью конвейера оболочки: стандартный ввод - это подписка,
стандартный вывод - издатель, а `producer | service | consumer` работает с обычными утилитами
командной строки.

```rust
--8<-- "crates/ruststream-sea-file/examples/stdio_pipeline.rs:pipeline"
```

Строки следуют формату клиента `[timestamp | stream_key | seq] payload`, поэтому ключ потока -
часть строки, и один процесс обслуживает несколько ключей:

```text
echo '[2024-01-01T00:00:00 | jobs | 1] {"id":7}' | ./pipeline run
```

`StdioBroker::new().loopback()` отправляет стандартный вывод этого процесса обратно в его же
стандартный ввод, поэтому stdio-сервис работает под тестом в одном процессе, без внешних команд.

## Тестирование {#testing}

Все наборы проверок в этом крейте выполняются локально, на временных файлах и внутрипроцессных
каналах, и запускать брокер не нужно.

Собственные обработчики вы проверяете обвязкой `TestApp` фреймворка против `FileTestBroker` из фичи
`testing`. Он держит в памяти сохраняемый журнал с позициями - то единственное свойство транспорта,
под которое написаны обработчики файла потока.

Поэтому сервис с перемоткой монтируется на него вообще без правок: `FileStream` здесь разрешается в
подписку, доставка сообщает `FilePosition`, а `FileContext` и `FileBatchContext` строятся на его
доставках так
же, как на доставках файла. Пакеты работают так же, поэтому пакетный обработчик видит пакеты того
размера, который запросила его точка монтирования.

Точке монтирования правки тоже не нужны. `Publish` - в обеих формах, `FilePublish` и
`StdioPublish`, - конструирует издателя против этого брокера, поэтому файл маршрутов сохраняет ту
политику, с которой поставляется, и `.out(Reply, Publish)` под обвязкой читается так же, как в
продакшене. Отдельной политики только для обвязки, которую надо было бы подставить, нет.

```rust
--8<-- "crates/ruststream-sea-file/tests/seek_context.rs:handler"
```

```rust
--8<-- "crates/ruststream-sea-file/tests/seek_context.rs:test"
```

Обвязка подаёт входные данные, доводит реакцию до состояния, когда в обработке ничего не осталось,
и записывает происходящее, поэтому тесту не нужны ни ожидания, ни собственный сборщик. Поверхность
проверок разобрана в разделе
[Юнит-тестирование сервиса через TestApp](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

Насколько велико сходство - измерено, а не заявлено. Наборы проверок контракта фреймворка -
последовательность переходов жизненного цикла, перемотка, пакетирование - выполняются и против
внутрипроцессного брокера, и против настоящего файла потока, поэтому контракт, который файл
соблюдает, а внутрипроцессная замена молча нарушила, не проходит в этом репозитории, а не в тестах
вашего сервиса.

Внутрипроцессный брокер подтверждает так же, как файл: `ack` и `nack` и там и там возвращают
`AckError::Unsupported`, поэтому обработчик, который читает ответ, ведёт себя одинаково. Не
воспроизводит он всё то, ради чего файл и нужен: сами файлы и маяки, метку конца потока, конверт
заголовков и временные характеристики. Всё это собственный набор проверок этого репозитория
прогоняет против настоящих файлов потоков.
